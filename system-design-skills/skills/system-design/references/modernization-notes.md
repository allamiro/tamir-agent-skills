# Modernization notes

The source book is dated May 2022 and is deliberately introductory. This file lists where
this library departs from or extends it. "Fetched 2026-10-14" means the source was read on
that date. "VERIFY" means the claim comes from author knowledge and must be checked before
being quoted as authoritative.

## Corrections of simplified book content (pp. 4–44, read)

| Topic | Book's simplified version | Library guidance | Basis |
|---|---|---|---|
| Password storage (13–15) | Store hash(password + salt); salt is not secret | Use a slow, memory-hard password hash (Argon2id first; scrypt; bcrypt for legacy; PBKDF2 when FIPS-140 is required). Per-user salt generated by the library. Optional pepper kept outside the database. Not a fast hash even when salted. OWASP minimum for Argon2id: 19 MiB memory, 2 iterations, parallelism 1; scrypt N=2^17, r=8, p=1; PBKDF2-HMAC-SHA-256 600,000 iterations; bcrypt work factor at least 10 and 72-byte input limit | OWASP Password Storage Cheat Sheet — fetched 2026-10-14 |
| HTTPS (16–17) | Client encrypts a session key with the server's public key | That is TLS 1.2 RSA key transport. TLS 1.3 removes static RSA and static Diffie-Hellman suites; all public-key key exchange provides forward secrecy; handshake messages after ServerHello are encrypted; 0-RTT early data has no non-replay guarantee between connections | RFC 8446 §1.2 and §2.3 — fetched 2026-10-14 |
| TLS handshake round trips | n/a | One round trip before application data in a full TLS 1.3 handshake | Author knowledge, VERIFY |
| SSO (11–12) | Bespoke token validated by calling back to the auth server | OpenID Connect over OAuth 2.0 with authorization code and PKCE; validate signature, issuer, audience, expiry, nonce. OAuth security BCP: PKCE for public clients, avoid implicit grant, exact redirect-URI matching, rotate or sender-constrain public-client refresh tokens | RFC 9700 — fetched 2026-10-14 |
| API HMAC auth (35–37) | HMAC with MD5/SHA-256 as examples; timestamp in signature | HMAC-SHA-256 or stronger over a canonical request, timestamp plus nonce replay protection, constant-time comparison, per-client key rotation; consider HTTP Message Signatures (RFC 9421) | RFC 9421 — VERIFY |
| Isolation levels (4–5) | Serializable = executed in sequence; names behave alike | Standard names, engine-specific behavior. PostgreSQL: Read Uncommitted behaves as Read Committed; Repeatable Read is snapshot isolation (no phantoms, but serialization anomalies such as write skew possible, with retryable `could not serialize access` errors); Serializable uses Serializable Snapshot Isolation and requires retry on SQLSTATE 40001. MySQL InnoDB: default Repeatable Read, snapshot from first read, gap/next-key locks for locking reads, plain SELECT becomes SELECT … FOR SHARE under Serializable with autocommit off | PostgreSQL 18 docs §13.2; MySQL 8.4 manual — fetched 2026-10-14 |
| Deployment (30–31) | Blue-green framed as staging (blue) vs production (green) | Blue-green is two production-capable stacks with a traffic switch; staging is a separate earlier environment; the shared database is the hard part. Add rolling, feature flags, shadow traffic, expand/contract migrations, two-phase format changes | AWS Builders' Library rollback safety — fetched 2026-10-14 |
| Orchestration (38–39) | Orchestration has built-in transaction management and reliability | The orchestrator centralizes visibility but a failed step still needs designed compensation (sagas); it is a throughput and availability dependency | Library synthesis, T2 |
| HTTP/Twitter/Google Docs (24–29) | Dated or name-only | Treated as illustrations. No algorithm trade-offs asserted for OT, DS or CRDT | n/a |

## Modern extensions where the book's coverage is TOC-anchored only

These entries correct or extend likely simplifications **without** asserting what the book
says. When the PDF is read, compare.

| Topic | Library position | Basis |
|---|---|---|
| Distributed "exactly-once" | Three guarantees; exactly-once within Kafka read-process-write requires idempotent producer, transactions, `read_committed` consumers and offsets committed in the transaction; exactly-once to external systems needs cooperation of the destination; always design idempotent consumers | Apache Kafka design docs (docs/design/design.md in the apache/kafka repository) — fetched 2026-10-14 |
| Object storage consistency | S3 provides strong read-after-write for PUT/DELETE and listings; per-key atomicity; no cross-key atomic update; no locking for concurrent writers (last-writer-wins); bucket configuration changes are eventually consistent. Other providers may differ | AWS S3 user guide — fetched 2026-10-14 |
| Object-store checksums, multipart limits | Verify end-to-end checksums; multipart part-size and count limits exist | Author knowledge, VERIFY |
| Redis persistence and eviction | RDB snapshots can lose minutes; AOF `everysec` can lose about one second; `allkeys-lru` is a suggested default for hot-subset workloads; replication/AOF buffers are not counted against `maxmemory`; LRU is approximated by sampling | Redis docs — fetched 2026-10-14 |
| Memcached | Simple key-value, no replication among servers, client-side distribution, LRU | Memcached site — fetched 2026-10-14 (partial) |
| Retries | Retry at one layer; exponential backoff with jitter; retry budgets; only idempotent operations; deadline propagation; load shedding to stop cascades | AWS Builders' Library; Google SRE book chapter — fetched 2026-10-14 |
| SLO alerting | Multi-window, multi-burn-rate alerts: 14.4× over 1 h/5 min (2% of budget), 6× over 6 h/30 min (5%), 1× over 3 d/6 h (10%), for 99.9%/30 days | Google SRE Workbook — fetched 2026-10-14 |
| Prometheus | Pull model, discovery, push gateway for short-lived jobs, not for 100%-accurate billing data | Prometheus docs — fetched 2026-10-14 |
| Payment idempotency | Providers save the first response per key and return it on retry; reusing a key with different parameters errors; keys may be pruned (at least 24 h in one provider's docs); not all failures are saved | Stripe API docs (one example provider) — fetched 2026-10-14 |
| PCI DSS | Scope applies to entities that store, process or transmit cardholder data; v4.x is current on the standards-body page; confirm scope and version with your assessor | PCI SSC page — fetched 2026-10-14 |
| HTTP/2 and HTTP/3 | HTTP/2 multiplexes streams over one TCP connection (transport head-of-line blocking remains); HTTP/3 runs over QUIC | Author knowledge; RFC 9113, 9114, 9000 — VERIFY |
| Historical figures | No performance figures or "latency numbers" are carried over from the book; any benchmark must be measured on your workload | Library policy |
