# Identity and security architecture

## Purpose and activation

Establish who is calling (authentication), what they may do (authorization), how data and
secrets are protected, and what attackers can try. Activate for any design with user
accounts, external APIs, multi-tenancy, sensitive data, or when asked for a threat model.
The source book's explanations of SSO, passwords, HTTPS and API signing are introductory;
this skill applies current practice (see corrections in the table below).

## Required inputs

User and client types (browser, mobile, server, third party), data classification (PII,
financial, health), tenancy model, compliance regime, existing identity provider, and
deployment environment. Missing: assume a public web/API product with PII, multi-tenant,
managed cloud, and use an external identity provider where possible.

## Workflow

1. **Inventory assets and trust boundaries**: data stores, secrets, privileged functions,
   each network and process boundary, third parties. Fill section 1 of
   `../system-design/assets/templates/security-architecture-checklist.md`.
2. **Threat-model each boundary with STRIDE** (Spoofing, Tampering, Repudiation,
   Information disclosure, Denial of service, Elevation of privilege). Record threat,
   mitigation, owner. Abuse cases first for money, data export, admin functions.
3. **Choose authentication** (matrix below). Prefer a managed/standard identity provider
   over building login.
4. **Design authorization**: model, enforcement points, object-level checks, tenant
   isolation. Default deny.
5. **Protect data in transit and at rest**: TLS policy, certificate management, encryption
   keys and rotation, secrets storage.
6. **Secure the API surface**: input validation, rate limits, request signing for
   machine clients, webhook verification, CORS/CSRF.
7. **Audit and detect**: security event log schema, retention, alerts.
8. **Walk the checklist** and convert every `N` into a finding with severity.

## Decision framework

### Where the book needs modernizing

| Topic | Book's introductory pattern (p.) | Use instead |
|---|---|---|
| Password storage | hash(password + salt) (13-15) | Slow, memory-hard password hash (Argon2id), unique salt generated by the library, optional pepper kept outside the database; never a fast hash such as SHA-256 or MD5 even when salted. Parameters: [references/modern-auth-reference.md](references/modern-auth-reference.md) |
| HTTPS | Client encrypts a session key with the server's public key (16-17) - TLS 1.2 RSA key transport | TLS 1.3: static RSA and static Diffie-Hellman suites removed; every key exchange gives forward secrecy; handshake messages after ServerHello are encrypted |
| SSO | Bespoke token validation callback (11-12) | OpenID Connect on OAuth 2.0: authorization code flow with PKCE, validated ID token claims |
| Request signing | HMAC with MD5/SHA256 examples (35-37) | HMAC-SHA-256 or stronger over a canonical request, with timestamp + nonce, constant-time comparison, key rotation; consider the HTTP Message Signatures standard (RFC 9421, VERIFY) |

### Authentication choice

| Situation | Choose | Why / caveat |
|---|---|---|
| Human users, web or mobile | OpenID Connect via an identity provider; authorization code + PKCE | Delegates credential handling, MFA, SSO, account recovery |
| Own username/password (unavoidable) | Argon2id hashing, MFA, rate limiting, breached-password check | You own the breach liability |
| Service-to-service inside your platform | mTLS or short-lived signed tokens from a workload identity system | Avoid long-lived shared secrets |
| Third-party server integrations | OAuth 2.0 client credentials with scopes, or HMAC-signed requests | HMAC suits simple partner APIs; keys need rotation and per-client revocation |
| Public read-only data | None, with rate limits | Still protect against abuse |

Sessions: browser cookie sessions need `Secure`, `HttpOnly`, `SameSite`, rotation on
login, server-side revocation; token-based APIs need short access-token lifetimes and
refresh-token rotation or sender-constrained tokens (RFC 9700 guidance, fetched 2026-10-14:
use PKCE, avoid the implicit grant, exact redirect-URI matching, rotate or sender-constrain
public-client refresh tokens).

### Authorization model

| Model | Use when | Risk |
|---|---|---|
| RBAC (roles) | Few stable roles | Role explosion; coarse |
| ABAC (attributes/policies) | Context-dependent rules (time, tenant, risk) | Policy complexity, testing |
| ReBAC (relationships) | Sharing/ownership graphs (docs, orgs) | Needs a relationship store and consistency design |

Always combine with **object-level checks**: "may this caller access *this* record?" - the
most common API flaw is checking only that the caller is logged in.

### Tenant isolation

| Mechanism | Isolation | Cost |
|---|---|---|
| Shared tables with tenant id + enforced filter (row-level security) | Logical | Cheapest; one missed filter leaks data - enforce in the data layer, test cross-tenant |
| Schema per tenant | Stronger logical | Migration fan-out |
| Database/account per tenant | Strongest | Operational cost, scale limits |

Choose by data sensitivity, tenant count, noisy-neighbor tolerance, compliance.

## Architecture and implementation guidance

- **Edge**: TLS termination with managed certificates and automated renewal; HSTS; WAF and
  rate limiting at the edge; only intended ports open.
- **Identity provider** issues short-lived tokens; services validate signature, `iss`,
  `aud`, `exp` (and `nonce` for ID tokens), algorithm allow-list; fetch signing keys via
  the provider's key set with caching and rotation handling.
- **Passwords**: Argon2id at OWASP's current minimum or higher, tuned so verification
  takes a bounded, measured time on your hardware; store the encoded hash string (it embeds
  algorithm, parameters, salt); rehash on login when parameters are upgraded; cap input
  length to avoid DoS; rate limit by account and IP; never log or email passwords.
- **Secrets**: from a secret manager at runtime, scoped per service, rotated, never in
  source or images; separate keys per environment.
- **Encryption at rest**: managed keys, envelope encryption for sensitive columns,
  separate key access from data access.
- **Webhooks and signed requests**: verify signature over raw body, check timestamp window
  (for example 5 minutes), keep a nonce/id cache to reject replays, compare in constant time.
- **Audit log**: who, what, which object, from where, outcome; append-only store with
  limited write path; correlation ids, no secrets or full PII in the log.
- **Privacy**: data minimization, retention limits, deletion path, region constraints.

## Failure and edge cases

- Token theft: short lifetimes, rotation, revocation list or introspection for critical
  actions, sender-constrained tokens.
- Confused deputy / IDOR: authorization based on caller identity from the token, never an
  id supplied in the request alone.
- Key compromise or rotation: dual-key validity window; revoke path rehearsed.
- Clock skew breaking signature and token validation: allow a small, explicit leeway.
- Account recovery as the weakest link (email takeover, SMS swap): design recovery with
  same strength as login.
- Enumeration through error messages/timing on login and reset flows.
- Replay of signed requests within the window without a nonce.
- 0-RTT early data in TLS 1.3 has no non-replay guarantee between connections (RFC 8446
  section 2.3): do not allow it for non-idempotent requests.
- Dependency/supply-chain compromise; over-privileged cloud roles.

## Validation

- Run the checklist; every `N` becomes a tracked finding.
- Automated: dependency scanning, secret scanning, SAST/DAST in CI.
- Authorization tests: for each endpoint, request as another user and another tenant;
  expect 403/404. Add these as regression tests.
- Measure password hash verification time at production parameters on production-like
  hardware; confirm it is within your latency budget and above your minimum cost target.
- Pen-test or threat-model review before launch for high-risk systems.
- Falsifier: any cross-tenant read, any token accepted after expiry/with wrong audience.

Security architecture section: asset/boundary table, STRIDE threat table with mitigations,
authentication and authorization design, key/secret management plan, completed
`security-architecture-checklist.md` with findings and severities, and ADRs for identity
provider and tenancy choices.
